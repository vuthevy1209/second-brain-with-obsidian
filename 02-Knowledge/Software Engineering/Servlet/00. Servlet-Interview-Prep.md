# Servlet Interview Preparation (Dành cho người đã học Spring Boot)

Tài liệu này được thiết kế để giúp bạn hiểu về Servlet, đặc biệt tập trung vào việc **bù đắp kiến thức nền tảng** khi bạn đã quen với Spring Boot. Trong Spring Boot, mọi thứ về Servlet đã được trừu tượng hóa và ẩn đi, nhưng các nhà tuyển dụng thường hỏi để kiểm tra xem bạn có hiểu "bản chất bên dưới" (under the hood) của Java Web hay không.

---

## 1. Servlet là gì?
**Servlet** là một class Java chạy trên server, có nhiệm vụ nhận Request từ client (thường là HTTP Request qua Browser), xử lý logic và trả về Response.

* **Container:** Servlet không thể tự chạy độc lập mà cần một môi trường gọi là **Servlet Container** (hay Web Container), phổ biến nhất là **Apache Tomcat** (được nhúng sẵn mặc định trong Spring Boot).
* **Mối liên hệ với Spring Boot:** Spring MVC (cốt lõi của Spring Boot Web) thực chất được xây dựng **dựa trên Servlet API**. Khi bạn viết một `@RestController` hay `@GetMapping`, bạn đang làm việc ở một tầng cao hơn, nhưng dưới cùng, mọi request đều đi qua một Servlet.

---

## 2. Tại sao học Spring Boot rồi vẫn bị hỏi về Servlet? (DispatcherServlet)

Đây là câu hỏi "ăn điểm" và thường được hỏi nhất.
Trong Java Web truyền thống, mỗi URL (ví dụ `/users`, `/orders`) sẽ được map với một class Servlet riêng biệt. Cách này rất khó quản lý khi dự án lớn.

**Spring (và Spring Boot) giải quyết việc này bằng mô hình Front Controller (DispatcherServlet):**
* **DispatcherServlet** chính là một Servlet! Nó đóng vai trò là điểm vào duy nhất (Front Controller) cho mọi HTTP request đi vào ứng dụng Spring Boot của bạn.
* Khi có request đến, Tomcat sẽ đẩy request đó cho `DispatcherServlet`.
* `DispatcherServlet` sẽ tra cứu (dựa vào `HandlerMapping`) xem request url này thuộc về Controller/Method nào (những chỗ bạn đánh dấu `@GetMapping`, `@PostMapping`...).
* Sau khi Controller xử lý xong, nó trả về dữ liệu (View hoặc JSON), `DispatcherServlet` sẽ đóng gói thành HTTP Response và trả về cho Tomcat để gửi cho client.

👉 **Câu trả lời ghi điểm:** *"Dù dùng Spring Boot em không trực tiếp cấu hình hay viết Servlet, nhưng em hiểu Spring MVC hoạt động dựa trên cơ chế Front Controller với `DispatcherServlet` là hạt nhân. Nó là một Servlet đứng ra nhận mọi request và điều phối đến các `@Controller` tương ứng."*

## 3. Vòng đời của một Servlet (Servlet Lifecycle)
*Đây là câu hỏi phỏng vấn kinh điển bậc nhất về Servlet.*

Vòng đời của Servlet do **Servlet Container (Tomcat)** quản lý, gồm 3 giai đoạn (tương ứng với 3 method):

1. **`init()` - Khởi tạo:**
   * Được gọi **DUY NHẤT MỘT LẦN** khi Servlet được tạo ra (thường là khi có request đầu tiên tới nó, hoặc khi server khởi động nếu cấu hình `load-on-startup`).
   * Dùng để khởi tạo tài nguyên (kết nối DB, đọc file config...).
2. **`service()` - Xử lý Request:**
   * Được gọi **MỖI KHI** có một request gửi đến Servlet.
   * Container tạo ra 2 object: `ServletRequest` và `ServletResponse` và truyền vào method này.
   * Trong `HttpServlet`, method `service()` sẽ kiểm tra loại HTTP Method (GET, POST, PUT...) và gọi tới các method tương ứng (`doGet()`, `doPost()`,...).
   * *Lưu ý:* Spring Boot `DispatcherServlet` ghi đè method này (cụ thể là `doService()`) để thực hiện logic phân phối request.
3. **`destroy()` - Hủy bỏ:**
   * Được gọi **DUY NHẤT MỘT LẦN** trước khi Servlet bị container tiêu hủy (khi shutdown server hoặc reload app).
   * Dùng để dọn dẹp tài nguyên (đóng kết nối DB, giải phóng bộ nhớ...).

## 4. Phân cấp Class/Interface của Servlet
Nhà tuyển dụng có thể hỏi về cấu trúc phân cấp để xem bạn có nắm rõ API không.

* **`Servlet` (Interface):** Chứa 3 method vòng đời ở trên (`init`, `service`, `destroy`).
* **`GenericServlet` (Abstract Class):** Implements `Servlet`. Nó độc lập với giao thức (không chỉ dành cho HTTP). Nó cung cấp implementation mặc định cho `init` và `destroy`, bạn chỉ cần implement `service()`.
* **`HttpServlet` (Abstract Class):** Kế thừa `GenericServlet` và được thiết kế **riêng cho giao thức HTTP**. Nó cung cấp sẵn logic trong `service()` để phân luồng request HTTP sang các method như `doGet`, `doPost`, `doPut`, `doDelete`.
  👉 *Trong thực tế, khi viết code Servlet thuần, ta luôn kế thừa `HttpServlet`.*

## 5. ServletConfig và ServletContext (Rất hay nhầm lẫn)

* **`ServletConfig`**: 
  * Phạm vi: **Riêng cho từng Servlet**.
  * Dùng để truyền các thông số cấu hình riêng (init-param) cho một Servlet cụ thể tại thời điểm khởi tạo (`init()`).
* **`ServletContext`**:
  * Phạm vi: **Toàn cục (Global) cho toàn bộ Web Application**.
  * Dùng để chia sẻ dữ liệu/thông số cấu hình chung cho tất cả các Servlet trong ứng dụng.

## 6. Session Management (Quản lý phiên làm việc)
Vì HTTP là giao thức **Stateless (không trạng thái)** (request sau không biết gì về request trước), nên cần cơ chế để nhận diện user qua nhiều request.

Có 4 cách quản lý Session trong Servlet (và Java Web nói chung):
1. **Cookies:** Lưu dữ liệu text nhỏ ở phía Browser (Client). Mỗi lần request, Browser tự động gửi Cookie lên Server. (Có rủi ro bảo mật nếu lưu dữ liệu nhạy cảm).
2. **HttpSession (Quan trọng nhất):** 
   * Dữ liệu được lưu ở **Server**. 
   * Server tạo ra một chuỗi ID duy nhất gọi là `JSESSIONID` và gửi về Client qua Cookie. Các request sau Client chỉ gửi `JSESSIONID` này lên, Server sẽ tra cứu ra phiên làm việc tương ứng.
3. **URL Rewriting:** Nối thẳng `JSESSIONID` vào cuối URL (dùng khi client tắt tính năng Cookie). VD: `http://abc.com/home;jsessionid=12345`.
4. **Hidden Form Fields:** Dùng một input ẩn `<input type="hidden">` trong form HTML để truyền ID. Hiện nay rất ít dùng.

## 7. Filter và Listener

* **Filter (Bộ lọc):**
  * Đứng chặn **trước** khi Request vào đến Servlet, hoặc chặn **sau** khi Servlet trả về Response.
  * **Ứng dụng:** Kiểm tra xác thực (Authentication/Authorization), ghi log, nén dữ liệu, mã hóa, đổi character encoding (UTF-8).
  * Trong Spring Security, cơ chế bảo mật (như kiểm tra JWT token) thực chất được xây dựng bằng **một chuỗi các Filter (Filter Chain)** đứng trước `DispatcherServlet`.
* **Listener (Bộ lắng nghe sự kiện):**
  * Lắng nghe các sự kiện xảy ra trong Web Container (như khi Server khởi động/tắt, khi một Session được tạo/hủy, khi có một attribute được thêm vào Request/Session).
  * **Ứng dụng:** Đếm số người đang online (SessionListener), khởi tạo dữ liệu chung khi server vừa chạy xong (ServletContextListener).

## 8. Các Câu Hỏi Phỏng Vấn (Q&A) Thường Gặp Khác

**Q1: Servlet có Thread-safe (an toàn luồng) không?**
👉 **Không.** Servlet Container chỉ tạo **MỘT instance duy nhất** (Singleton) cho mỗi khai báo Servlet. Khi có nhiều request đồng thời, Container tạo nhiều Thread và cho tất cả chạy chung qua một instance Servlet đó (gọi chung method `service()`). Do đó, nếu bạn khai báo **biến toàn cục (instance variable)** trong Servlet, nó sẽ dẫn đến lỗi tranh chấp dữ liệu (Race condition).
*(Lời khuyên: Chỉ dùng biến cục bộ bên trong method xử lý).*

**Q2: Sự khác nhau giữa `forward()` và `sendRedirect()`?**
* **`forward()` (RequestDispatcher):** Chuyển hướng ở **phía Server**. Client không hề biết sự chuyển hướng này (URL trên trình duyệt không đổi). Chỉ tốn 1 request HTTP. Dùng để chuyển xử lý từ Servlet này sang JSP/Servlet khác nội bộ.
* **`sendRedirect()` (HttpServletResponse):** Chuyển hướng ở **phía Client**. Server trả về status code 302 kèm URL mới. Browser tự động tạo một HTTP request MỚI đến URL đó (URL trên trình duyệt bị thay đổi). Tốn 2 request HTTP.

**Q3: Kể tên các HTTP Status Code phổ biến mà Servlet/Spring trả về?**
* `200 OK`: Thành công.
* `201 Created`: Tạo mới thành công (thường dùng trong REST API).
* `400 Bad Request`: Lỗi cú pháp từ client, validation fail.
* `401 Unauthorized`: Chưa đăng nhập, thiếu token.
* `403 Forbidden`: Đã đăng nhập nhưng không đủ quyền.
* `404 Not Found`: Không tìm thấy URL.
* `500 Internal Server Error`: Lỗi logic code ở phía Server (NullPointerException,...).
