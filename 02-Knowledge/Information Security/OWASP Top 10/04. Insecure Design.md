# A04: Insecure Design (Thiết kế không an toàn)

## 1. Khái niệm
Insecure Design (Thiết kế không an toàn) khác biệt với các lỗ hổng khác ở chỗ: Nó không phải là do lỗi lập trình (bug) mà là do thiếu sót hoặc **sai lầm về mặt logic, kiến trúc (Business logic flaw)** ngay từ khâu thiết kế. Một ứng dụng có thể được code rất hoàn hảo, không có lỗi injection hay XSS nào, nhưng vẫn bị xâm phạm do thiết kế quy trình nghiệp vụ có lỗ hổng.

## 2. Ví dụ lỗ hổng thiết kế (Vulnerable Design)

**Ngữ cảnh:** Ứng dụng bán vé máy bay có chức năng đặt vé, nhưng không thiết kế cơ chế giới hạn số lượng request hoặc giới hạn số vé được mua cùng lúc (Rate Limiting/Anti-automation). 

Kẻ tấn công có thể viết một đoạn script nhỏ gọi API đặt vé liên tục để mua toàn bộ số vé trên hệ thống trong vài giây (ngăn chặn người khác mua hoặc dùng để đầu cơ).

```java
@RestController
@RequestMapping("/api/booking")
public class BookingController {

    @Autowired
    private TicketService ticketService;

    // LỖ HỔNG THIẾT KẾ: API hoàn toàn không có cơ chế chặn Bot
    // Không có captcha, không giới hạn rate limit.
    @PostMapping("/book")
    public ResponseEntity<String> bookTicket(@RequestBody BookingRequest request) {
        
        boolean success = ticketService.processBooking(request);
        if (success) {
            return ResponseEntity.ok("Booking successful!");
        }
        return ResponseEntity.badRequest().body("Failed");
    }
}
```

## 3. Thiết kế an toàn (Secure Design)

Chúng ta phải đưa các cơ chế bảo mật vào luồng logic. Ví dụ: giới hạn số lượng request bằng **Rate Limiting**, yêu cầu **CAPTCHA** đối với các hành động quan trọng, hoặc giữ chỗ (Lock) giới hạn thời gian.

Ví dụ tích hợp Rate Limiting bằng thư viện `Bucket4j` trong Spring Boot để chặn Bot:

```java
import io.github.bucket4j.Bandwidth;
import io.github.bucket4j.Bucket;
import io.github.bucket4j.Bucket4j;
import io.github.bucket4j.Refill;
import java.time.Duration;

@RestController
@RequestMapping("/api/booking")
public class SecureBookingController {

    // Tạo bucket: Cho phép tối đa 5 requests mỗi phút
    private final Bucket bucket;

    public SecureBookingController() {
        Bandwidth limit = Bandwidth.classic(5, Refill.greedy(5, Duration.ofMinutes(1)));
        this.bucket = Bucket4j.builder().addLimit(limit).build();
    }

    @PostMapping("/book")
    public ResponseEntity<String> bookTicketSecure(@RequestBody BookingRequest request) {
        // CODE AN TOÀN: Kiểm tra Rate Limit trước khi thực thi logic nghiệp vụ
        if (bucket.tryConsume(1)) {
            // Còn token, cho phép đặt vé
            boolean success = ticketService.processBooking(request);
            return ResponseEntity.ok("Booking successful!");
        } else {
            // Hết token (Vượt quá 5 request/phút)
            return ResponseEntity.status(HttpStatus.TOO_MANY_REQUESTS)
                                 .body("Bạn thao tác quá nhanh. Vui lòng thử lại sau.");
        }
    }
}
```

## 4. Cách phòng chống khác
- Áp dụng **Mô hình hóa mối đe dọa (Threat Modeling)** ở giai đoạn phân tích yêu cầu hệ thống.
- Sử dụng CAPTCHA (như reCAPTCHA) cho luồng đăng ký, đặt hàng, khôi phục mật khẩu.
- Không sử dụng các câu hỏi bảo mật dễ đoán để khôi phục mật khẩu (ví dụ "Tên con cún của bạn là gì?").
- Bắt buộc kiểm tra tính hợp lệ của nghiệp vụ (Business Rule Validation) liên tục.
