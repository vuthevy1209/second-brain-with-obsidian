# A02: Cryptographic Failures (Lỗi mã hóa)

## 1. Khái niệm
Cryptographic Failures (trước đây là Sensitive Data Exposure) xảy ra khi các dữ liệu nhạy cảm (mật khẩu, số thẻ tín dụng, thông tin y tế, token...) không được bảo vệ đúng cách bằng các biện pháp mã hóa tiêu chuẩn.
Lỗi này bao gồm việc lưu trữ dữ liệu dưới dạng plain-text (rõ chữ), sử dụng thuật toán băm/mã hóa đã lỗi thời (MD5, SHA-1), hoặc sử dụng sai cách các thư viện mã hóa.

## 2. Code ví dụ lỗ hổng (Vulnerable Code)

Dưới đây là một ví dụ bằng `Java` sử dụng thuật toán băm lỗi thời để lưu trữ mật khẩu:

```java
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.HexFormat;

public class InsecureCrypto {
    
    public void registerUser(String username, String password) {
        try {
            // LỖ HỔNG: Sử dụng thuật toán băm lỗi thời (MD5) và KHÔNG có Salt (muối)
            MessageDigest md = MessageDigest.getInstance("MD5");
            md.update(password.getBytes());
            byte[] digest = md.digest();
            
            // Chuyển mảng byte sang chuỗi Hex (Yêu cầu Java 17+)
            String passwordHash = HexFormat.of().formatHex(digest);
            
            // Lưu vào database (Ví dụ: lưu thẳng chuỗi hash)
            // userRepository.save(new User(username, passwordHash));
            System.out.println("Saved hash cho user " + username + ": " + passwordHash);
            
        } catch (NoSuchAlgorithmException e) {
            e.printStackTrace();
        }
    }
}
// Gọi hàm: registerUser("admin", "123456");
// Output: Saved hash cho user admin: e10adc3949ba59abbe56e057f20f883e
```

### Giải thích nguyên nhân:
1. **Thuật toán MD5 đã bị bẻ khóa:** MD5 tính toán rất nhanh, kẻ tấn công có thể dễ dàng dùng các loại card đồ họa (GPU) để chạy hàng tỷ phép thử mỗi giây (Brute-force) để dò ra mật khẩu gốc.
2. **Không có Salt (Muối):** Việc băm trực tiếp `123456` luôn ra chuỗi hash `e10adc...`. Kẻ tấn công chỉ cần dùng "Rainbow Tables" (bảng tra cứu chứa sẵn hàng triệu mã băm của các mật khẩu phổ biến) là có thể ngay lập tức đối chiếu và tìm ra mật khẩu gốc.

## 3. Code an toàn (Secure Code)

Để bảo vệ mật khẩu, chúng ta phải sử dụng các thuật toán chậm, được thiết kế chuyên biệt cho việc băm mật khẩu (như **bcrypt**, **Argon2**, **PBKDF2**) và phải **luôn có Salt ngẫu nhiên**.

Trong hệ sinh thái Java/Spring, chúng ta thường sử dụng `BCryptPasswordEncoder` của Spring Security:

```java
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;

public class SecureCrypto {
    
    // Spring Security cung cấp sẵn class này để băm mật khẩu bằng thuật toán bcrypt
    private final BCryptPasswordEncoder passwordEncoder = new BCryptPasswordEncoder();
    
    public void registerUserSecure(String username, String password) {
        // CODE AN TOÀN: Hàm encode() sẽ TỰ ĐỘNG sinh ra một chuỗi Salt ngẫu nhiên 
        // và gộp chung thuật toán, độ khó, salt và mã băm vào chuỗi kết quả cuối cùng.
        String passwordHash = passwordEncoder.encode(password);
        
        // Lưu vào database
        // userRepository.save(new User(username, passwordHash));
        System.out.println("Saved hash an toàn: " + passwordHash);
    }
    
    public void verifyLogin(String passwordInput, String storedHash) {
        // CODE AN TOÀN: Hàm matches() tự động tách Salt từ storedHash ra và tính toán lại 
        // mật khẩu người dùng nhập vào để đối chiếu một cách an toàn.
        if (passwordEncoder.matches(passwordInput, storedHash)) {
            System.out.println("Đăng nhập thành công!");
        } else {
            System.out.println("Sai mật khẩu!");
        }
    }
}
```

### Giải thích cách khắc phục:
1. **Sử dụng bcrypt:** `bcrypt` được thiết kế để chạy chậm có chủ ý (thông qua cơ chế Work Factor / Cost). Điều này khiến việc tấn công Brute-force bằng GPU trở nên vô cùng tốn thời gian và không khả thi.
2. **Tự động dùng Salt ngẫu nhiên:** Thuật toán bcrypt tạo ra một chuỗi Salt ngẫu nhiên cho **mỗi lần băm**. Dù hai người có cùng mật khẩu `123456`, mã băm lưu trong CSDL của họ vẫn sẽ hoàn toàn khác nhau. Điều này vô hiệu hóa các cuộc tấn công bằng Rainbow Tables.

## 4. Cách phòng chống khác
- **Data in Transit (Truyền tải):** Bắt buộc sử dụng giao thức HTTPS (TLS 1.2 hoặc 1.3) cho mọi kết nối thay vì HTTP. Bật cờ HSTS (HTTP Strict Transport Security).
- **Data at Rest (Lưu trữ):** Không lưu trữ dữ liệu nhạy cảm nếu không thật sự cần thiết. Nếu phải lưu trữ (như số thẻ tín dụng), hãy dùng các chuẩn mã hóa mạnh như **AES-256-GCM** với hệ thống quản lý Key chuyên dụng (KMS) hoặc JCA (Java Cryptography Architecture) theo đúng chuẩn.
- Không tự chế tạo thuật toán mã hóa riêng (Don't roll your own crypto). Luôn dùng các thư viện đã được cộng đồng kiểm chứng kỹ lưỡng như Spring Security Crypto.
